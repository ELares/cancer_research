# Is a burden denominator reachable?

Generated by `scripts/burden_data_feasibility.py`. The census assigns 18 anatomical sites; dividing those counts by cancer burden would answer which cancers are under-researched relative to the harm they do. This asks whether the denominator exists in a form that join can use.

**Verdict: NOT feasible from the sources probed.**

| requirement | met |
|---|---|
| site resolved at census granularity | **no** |
| global not national | **no** |
| recent enough | **no** |
| reachable without registration | yes |

## What each source returns

**IARC Global Cancer Observatory (GLOBOCAN)** — the standard global site-resolved incidence and mortality series

- `https://gco.iarc.fr/gco-api/v1/cancers` → HTTP 200, html-or-other
- `https://gco.iarc.who.int/gco-api/analysis/today/data-population/900/` → HTTP 200, html-or-other
- `https://gco.iarc.fr/today/api/data/populations/900/` → HTTP 200, html-or-other
- `https://gco.iarc.fr/overtime/api/data/` → HTTP 200, html-or-other

**WHO Global Health Observatory (OData)** — login-free and well documented; already used for other WHO series

- `https://ghoapi.azureedge.net/api/Indicator?$select=IndicatorCode,IndicatorName` → HTTP 200, json

Every GCO route tried answers **HTTP 200 with the single-page-app shell**. That matters for how this was tested: a status check or an exit code would read those as a working API. The discriminator is whether the body parses as JSON, and none does. The documented API path has moved, and guessing further is not a method -- this repo has already hit the same failure with a DepMap catalogue that began serving HTML where it had served CSV.

## What WHO GHO covers

| census site | indicator | rows | years | global aggregate |
|---|---|--:|---|---|
| breast | `SA_0000001438` | 765 | 2002-2004 | **no** |
| colorectal | `SA_0000001439` | 762 | 2002-2004 | **no** |
| head and neck | `SA_0000001448` | 763 | 2002-2004 | **no** |
| liver | `SA_0000001445` | 762 | 2002-2004 | **no** |
| oesophagus | `SA_0000001449` | 758 | 2002-2004 | **no** |

5 of 18 census sites have a site-resolved mortality indicator, the most recent data is 2004, and there is no global aggregate -- the series is country-level. Missing entirely: `bladder`, `brain/CNS`, `cervix/uterus`, `kidney`, `leukaemia`, `lung`, `lymphoma`, `ovary`, `pancreas`, `prostate`, `skin/melanoma`, `stomach`, `thyroid`.

These are also not a general cancer-mortality panel. They belong to an alcohol-attributable-burden series, which is why the covered sites are the alcohol-associated ones and why the panel stops where it does. Dividing 2026 literature counts by a 2004 country-level alcohol-attributable subset, and presenting the result as research effort per death, would be worse than not asking -- the number would look like an answer.

## What would unblock it

One thing: a site-resolved global cancer mortality table that can be committed as a derived artifact. GLOBOCAN is the right source and its data are downloadable through the web interface; what is missing is a documented machine route to them. Any of these closes the gap:

- a GLOBOCAN export saved by hand and committed, with its retrieval date and the exact selection recorded, exactly as the CTRPv2 and cBioPortal legs are handled here;
- the current GCO API path, if IARC documents one;
- an IHME GBD extract, which is site-resolved and global but needs registration, so it would have to be fetched once and committed.

## What this does NOT say

It does not say the ratio would be a good measure once the data arrived. Literature is global but concentrated in high-income research systems while mortality is not, so a low ratio could mean neglect or could mean the disease's burden falls where research does not happen -- a distinction the ratio alone cannot make. Incidence and mortality also diverge sharply by site, and a cancer that is already curable rationally attracts less new work. Those confounds are arguments for how to report the ratio, not reasons to skip it, but they should be settled before the number is computed rather than after.
